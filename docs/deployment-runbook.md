# VYRALIS Deployment and Operations Runbook

## Current repository reality
The root Dockerfile builds the FastAPI API and installs FFmpeg; it does not build or serve the React frontend. The current SQLite API is a single-workspace foundation without authentication or tenant isolation. Do not expose it publicly as a multi-user production service.

## Local development
Requirements: Python 3.11, Node.js 20+, FFmpeg and FFprobe.
1. Create and activate a Python virtual environment.
2. Install backend/requirements.txt.
3. Set VYRALIS_DATA_DIR to a persistent local directory.
4. Start FastAPI on loopback.
5. Install npm dependencies and run the Vite development server.
6. Set VITE_API_BASE_URL to the local API.
7. Upload a rights-cleared test video and complete the core workflow.

## Render deployment (single instance, current codebase)

The `Dockerfile` is multi-stage: stage 1 builds the Vite studio, stage 2 installs FFmpeg
(with libass) and the Python engine, and FastAPI serves the studio build from the same
origin (`VYRALIS_WEB_DIR=/app/dist`). One service on Render is therefore enough, and
same-origin is what makes the access gate and OAuth callbacks work without extra wiring.

1. Push the repository to GitHub and create a Render **Blueprint** from it (`render.yaml`).
2. Set the required values:
   - `VYRALIS_PUBLIC_URL` — this service's URL, e.g. `https://vyralis-api.onrender.com`.
     OAuth redirect URIs are derived from it.
   - `VYRALIS_BASIC_AUTH` — `user:password` for the access gate. **Set this before the
     service is public:** the app is single-workspace and has no per-user accounts.
   - `VYRALIS_AUTH_SECRET` is generated by the blueprint; keep it stable, it encrypts
     provider tokens (rotating it disconnects every platform).
   - `VYRALIS_CORS_ORIGINS` only if you split the frontend onto another origin.
3. Deploy. Render builds the image, mounts the 20 GB disk at `/var/lib/vyralis` and checks
   `/api/health`.
4. Open the service URL: the browser asks once for the Basic credentials and then shows the
   studio, served by the same host.
5. Connect a platform from **Connections**; register
   `https://<api-host>/api/oauth/<platform>/callback` with the provider (`docs/oauth-setup.md`).

### Optional CDN split (Vercel)

If you want the frontend on Vercel instead, `vercel.json` is included for the SPA build.
In that case: deploy `dist/` to Vercel with `VITE_API_BASE_URL=https://<api-host>`, set
`VYRALIS_CORS_ORIGINS` to the Vercel origin, and **do not use HTTP Basic auth** — browsers
do not prompt for credentials on cross-origin API calls, so the studio would simply fail.
Cross-origin hosting needs the session-based auth that is not built yet.

### Operational notes

- **One instance only.** The queue is an in-process thread pool and the database is SQLite
  on the mounted disk. Two instances would double-run jobs and corrupt state.
- **Readiness vs liveness.** `/api/health` is the liveness check Render uses.
  `/api/ready` reports FFmpeg, FFprobe, yt-dlp, storage, database and whether a studio build
  is present; it returns 503 when storage or the database is broken. It sits behind the
  access gate, so a monitor needs the same Basic credentials as the studio.
- **Disk, not object storage.** Media lives on the disk and survives redeploys, but a lost
  disk loses media. Back up `/var/lib/vyralis` or move to object storage before relying on it.
- **First job is slow.** faster-whisper downloads the configured model on first use unless
  it is baked into the image. Expect a minute or two the first time.
- **Cost.** Starter + 20 GB disk is the minimum viable size. Whisper `base` on CPU handles
  short clips; long videos are slow. Raise the plan or lower the model for volume.
- **Build check.** The image build fails if Debian's FFmpeg lacks the `subtitles` filter, so
  a missing libass cannot reach production silently.
- **HTTPS is mandatory** for provider redirect URIs; Render provides it on `*.onrender.com`.

## Hosted deployment target (multi-tenant, not built yet)
Separate services:
- Frontend: static React build on a CDN/static host.
- API: FastAPI container behind HTTPS reverse proxy.
- Worker: separate process/container with FFmpeg and model dependencies.
- Database: managed PostgreSQL with migrations and automated backups.
- Queue: durable Redis-compatible queue or equivalent.
- Object storage: private bucket with signed URLs.
- Secrets: host-managed environment variables or secret manager.

## Configuration
VYRALIS_DATA_DIR, VYRALIS_CORS_ORIGINS, VYRALIS_MAX_UPLOAD_BYTES, VYRALIS_WORKERS,
VYRALIS_WHISPER_MODEL/DEVICE/COMPUTE, VYRALIS_PUBLIC_URL, VYRALIS_FRONTEND_URL,
VYRALIS_AUTH_SECRET (token encryption) and VYRALIS_BASIC_AUTH (hosted access gate).
Social platform clients: GOOGLE_CLIENT_ID/SECRET, TIKTOK_CLIENT_KEY/SECRET, META_APP_ID/SECRET,
X_CLIENT_ID/SECRET. Never commit real values; `.env.example` lists the full set.

## Release checklist
- [ ] Frontend build and typecheck pass.
- [ ] Backend compile and unit tests pass.
- [ ] Migrations apply on empty and existing databases.
- [ ] Worker restart recovery and retry tested.
- [ ] Upload and output checks pass on representative test media.
- [ ] Auth and tenant isolation verified before public exposure.
- [ ] HTTPS, CORS, rate limits, storage privacy and backups verified.
- [ ] Health/readiness checks distinguish API, database, queue, storage and worker.
- [ ] Logs redact tokens and private media URLs.
- [ ] Rollback image and migration plan documented.

## Operations
Monitor queue age, worker utilization, failure rate, processing time per media minute, upload rejection, render validation failures, storage and provider limits. Alert on stuck jobs, repeated retries, worker crashes, database exhaustion and storage thresholds.
